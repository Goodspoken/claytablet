# Спецификация: Реализация защиты комнат паролем

## Обзор
Цель этого трека — добавить **опциональную** возможность установки пароля для комнат PopyCast (смешанный режим). Это позволит создавать как полностью открытые комнаты (доступные только по ссылке), так и приватные пространства. Эта фича также закладывает архитектурный фундамент для будущей полноценной авторизации пользователей.

## Пользовательские сценарии
1. **Смешанный режим:** Пользователь может создать публичную комнату (без пароля) или приватную (с паролем).
2. **Публичная комната:** Работает как обычно — любой, у кого есть ссылка, имеет полный доступ.
3. **Приватная комната:** При попытке войти, система запрашивает пароль. Доступ ко всем данным блокируется до успешного ввода.
4. **Сохранение доступа:** После успешного ввода пароля, доступ сохраняется на время сессии (сохраняется токен).
5. **Управление:** Владелец комнаты (на данном этапе любой участник, в будущем — авторизованный создатель) может добавить, изменить или удалить пароль через настройки.

## Технические изменения

### Бэкенд
- Модель `room_configs` (или `RoomSettings`) получает опциональное поле `password_hash`.
- Если `password_hash` равно `None`, комната считается публичной (проверки пропускаются).
- Эндпоинт `/api/popycast/{room_id}/verify-password` проверяет пароль и возвращает сессионный токен доступа (на основе JWT или простого подписанного куки).
- Зависимость FastAPI (Dependency) `verify_room_access` защищает все эндпоинты `/api/popycast/...`.

### Фронтенд
- `SettingsModal` поддерживает опциональный ввод пароля.
- Новый компонент `PasswordPrompt`, который перехватывает ошибки `401 Unauthorized` от API.
- Хранение токенов доступа к комнатам в `sessionStorage` или `localStorage`.

## Задел на будущее
- Реализация `verify_room_access` должна быть спроектирована так, чтобы в будущем легко интегрировать глобальную проверку пользователя (User Auth), когда у комнат появятся постоянные владельцы.

## Критерии приемки
- Старые (и новые публичные) комнаты продолжают работать без изменений и запросов паролей.
- Защищенные комнаты отдают `401`, пока не передан корректный токен.
- Пароли хранятся на бэкенде только в виде безопасных хешей (bcrypt).
